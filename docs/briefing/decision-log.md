# Decision Log — PocketProfit (บันทึกค่าใช้จ่ายร้านค้าเล็ก, โจทย์ 02)

> ทุกการตัดสินใจสำคัญ + **ทำไม** + ทางเลือกที่ชั่งน้ำหนัก + tradeoff. อิงโค้ดที่สร้างจริง.
> ใช้สำหรับตอบ "ทำไมถึงทำแบบนี้?" / "ทำไมไม่ทำแบบนั้น?" ในเดโม.
> **แอป:** PocketProfit — แท็กไลน์ "รู้กำไรร้าน ทุกวัน" · รัน `:3200` · เดโม `napha@example.com / 123456789`

## A. Stack & สถาปัตยกรรม

| # | ตัดสินใจ | ทำไม | ทางเลือกที่ชั่ง | Tradeoff |
|---|----------|------|----------------|----------|
| A1 | **Next.js 15 App Router + Server Actions** (ไม่แยก REST API) | logic การเงินอยู่ฝั่ง server ทั้งหมด, ฟอร์มเรียก action ตรง ๆ → โค้ดน้อย ปลอดภัยกว่า client ส่ง JSON | แยก backend (Express/Nest) + REST | คุม Time ได้ดีกว่ามาก; แลกกับการ vendor-lock ที่ Next |
| A2 | **SQLite + Prisma** | MVP คนเดียว/ร้านเดียว ไม่ต้องตั้ง DB server, เดโม/seed ได้ใน 1 ไฟล์ | Postgres ตั้งแต่แรก | ย้ายเป็น Postgres ภายหลังแค่เปลี่ยน `datasource` (โค้ด query ไม่แตะ) — ดู roadmap |
| A3 | **เก็บเงินเป็น integer "สตางค์" ทุกที่** (`amountSatang`, `budgetSatang`…) | float baht ทำให้เกิด drift (0.1+0.2≠0.3) → กำไรเพี้ยนสะสม. integer คูณ/บวกไม่มี error | เก็บเป็น `Decimal` ของ Prisma | สตางค์เบากว่า, คำนวณเร็ว, ทุกภาษาเข้าใจ; แลกกับต้องแปลง ↔ บาท ที่ขอบ (มี `money.ts` คุมจุดเดียว) |
| A4 | **แยก `occurredAt` (วันเกิดรายการ) ออกจาก `createdAt` (เวลา insert)** | พี่นภาบันทึกย้อนหลังได้ → ยอดต้องลง"วันที่เกิดจริง" ไม่ใช่วันที่กรอก. สรุปวัน/เดือน group ด้วย `occurredAt` | ใช้ `createdAt` อย่างเดียว | back-date ลงเดือนถูกต้อง; แลกกับ 1 คอลัมน์เพิ่ม + index `(userId, occurredAt)` |
| A5 | **denormalize `categoryName` ลงในทุก Entry** (snapshot) | ถ้าหมวดถูกแก้ชื่อ/ลบ (N2) รายการเก่ายัง"อ่านออก"ตามชื่อ ณ ตอนบันทึก — audit ไม่เพี้ยน | join Category ทุกครั้ง | ประวัติคงที่ + query เร็ว; แลกกับชื่อหมวดไม่ sync ย้อนหลัง (ตั้งใจ — นั่นคือ snapshot) |

## B. Money math — กันยอดเพี้ยน (Output Quality + เชื่อใจตัวเลข)

| # | ตัดสินใจ | ทำไม | Tradeoff/ทางเลือก |
|---|----------|------|--------------------|
| B1 | **แปลงบาท→สตางค์ด้วย `Math.round(n*100)` จุดเดียวใน `money.ts`** | กันจุดแปลงกระจัดกระจาย; ทุก write ผ่านจุดเดียว | ทำให้ test/แก้ง่าย |
| B2 | **กราฟ/ตัวเลขทุกจุดผ่าน `formatBaht`/`formatMoney` ที่กัน NaN → "0"** (รวม count-up: `AnimatedMoney` guard `Number.isFinite`) | empty state / ค่าหาย ไม่โชว์ `NaN`/`฿NaN` เด็ดขาด — แม้แต่ตอน animate ก็ปลอดภัย | เลือก fail-safe เป็น 0 มากกว่า throw |
| B3 | **กำไร < 0 → สีแดง + เครื่องหมาย "−" + ▼ + ข้อความ "วันนี้ขาดทุน ไม่เป็นไร พรุ่งนี้สู้ใหม่"** (`formatSignedMoney`, `profit-hero.tsx` tone="auto") | พี่นภา color-blind-safe ต้องเห็นทันทีว่าขาดทุน ไม่พึ่งสีอย่างเดียว; ประโยคให้กำลังใจ (ดู BR5) | a11y + ชัด; โค้ดเช็ค `net<0` ทุกการ์ด |
| B4 | **VAT แบบ inclusive**: `amountSatang` = ยอดรวม VAT แล้ว, แยก `vatAmountSatang` ด้วย `total − total/(1+rate)` | พี่นภากรอกยอดที่จ่ายจริง (รวม VAT อยู่แล้วบนใบเสร็จ) ไม่ต้องคิดแยกเอง | ตรงพฤติกรรมจริง; ถ้าจะทำ exclusive ต้องให้ผู้ใช้คิดเอง = ผิด persona |

## C. เวลา / การตัดยอด (Asia/Bangkok)

| # | ตัดสินใจ | ทำไม | ทางเลือก/Tradeoff |
|---|----------|------|--------------------|
| C1 | **ตัดยอด "วันนี้/เดือนนี้" ตามเวลาไทย (UTC+7) ไม่ใช่ UTC/เวลาเครื่อง** (`dates.ts` ทั้งไฟล์) | บันทึก 5 ทุ่มไทย = วันเดิม; ถ้าใช้ UTC จะข้ามไปวันถัดไป → ยอด"วันนี้"ผิด | คำนวณ offset เอง (ไม่พึ่ง lib timezone หนัก ๆ) — เบา, deterministic |
| C2 | **เก็บ `occurredAt` เป็น instant ที่ "เที่ยงวันไทย" (05:00Z) ของวันนั้น** | เที่ยงวันอยู่กลางวันไทยเสมอ → ไม่มีทางปัด/DST ทำให้ข้ามวัน | กันเคสขอบ; ผู้ใช้ไม่เห็นเวลา (เก็บแค่"วัน") |
| C3 | **`bkkMonthRange`/`bkkDayRange` คืน `[gte, lt)` แล้วใช้ filter ที่ DB** | group/sum ที่ DB เร็วและถูก ไม่ต้องดึงทั้งหมดมา group ใน JS | scale ดีกว่า; โค้ด query สะอาด |
| C4 | **`Goal.month` / `RecurringSkip.month` เก็บเป็น string "YYYY-MM" (เวลาไทย)** | คีย์เดือนที่มนุษย์อ่านออก + unique ต่อผู้ใช้ต่อเดือนง่าย | เทียบ/หาเดือนก่อนด้วย string ตรง ๆ |

## D. Validation (zod เดียวกัน client+server) — เก็บแต้ม Output Quality 20%

| # | ตัดสินใจ | ทำไม | Tradeoff |
|---|----------|------|----------|
| D1 | **zod schema ชุดเดียวใน `validation.ts` ใช้ทั้ง 2 ฝั่ง** | client = ตอบไว (react-hook-form), server = re-validate กัน bypass → ปลอดภัย + ข้อความตรงกันเป๊ะ | ต้องออกแบบ schema ให้รับ string จาก input |
| D2 | **ข้อความ error เป็นภาษาไทยเจาะจง** (เช่น "กรอกเป็นตัวเลขเท่านั้น") | พี่นภาไม่รู้ศัพท์ → ดีกว่า "invalid input". ตรวจได้ในเดโม | ต้อง maintain ข้อความ แต่คุ้มแต้ม |
| D3 | **จำนวนเงิน: บล็อก ว่าง/ตัวอักษร/≤0/ติดลบ/ทศนิยม>2/>10,000,000** ตามลำดับ refine | ครอบ proactive edge "กรอกเลขเพี้ยน" + "เพดานเงิน" ที่โจทย์ไม่ได้สั่งแต่เพิ่มเอง | เลขมหาศาลถูกกันที่ 10M (เกินจริงของร้านชำ) |
| D4 | **วันที่อนาคต = บล็อก** (`v <= todayDateKey()`) | บันทึกบิลที่"ยังไม่เกิด"ไม่สมเหตุผล | เลือกบล็อกแทนเตือน (เข้มกว่า ปลอดภัยกว่าสำหรับยอด) |
| D5 | **เหตุผลแก้ไขบังคับ ≥ 3 ตัวอักษร** (`editReasonSchema`) | EDGE-1: audit ต้องมีเหตุผลจริง ไม่ใช่เคาะ space | กัน reason ขยะ; 3 ตัวพอ ไม่กวนผู้ใช้ |

## E. Auth + per-user isolation (บังคับ — ทุก build เป็น multi-user)

| # | ตัดสินใจ | ทำไม | Tradeoff |
|---|----------|------|----------|
| E1 | **Session = random token 32 bytes ใน DB + cookie httpOnly, sameSite=lax, 30 วัน** (`auth.ts`) | กว่า JWT ฝั่ง client: เพิกถอนได้ (ลบ row), token ไม่มี payload หลุด | ต้อง query DB ต่อ request (ยอมรับได้ที่ scale นี้) |
| E2 | **`requireUser()` ทุกหน้าใน `(app)/` + redirect ไป `/login` ถ้าไม่มี session** (AUTH-5) | กันเปิด URL ตรงโดยไม่ login | layout-level guard + middleware ป้องกัน 2 ชั้น |
| E3 | **ทุก query ผูก `userId` เสมอ** (`queries.ts` ทุกฟังก์ชัน) — read & write | AUTH-3: ผู้ใช้ A ไม่มีทางเห็น/แก้ของ B แม้รู้ id (กัน IDOR) | วินัยตายตัว; tech-lead verify แล้วว่า bound ครบ |
| E4 | **getEntryWithRevisions / fetchRevisions / deleteEntry ใช้ `findFirst({id, userId})`** | กัน IDOR เฉพาะจุดที่รับ id จาก client | เช็ค ownership ก่อนทุก action |
| E5 | **bcrypt cost 10** ทั้ง runtime และ seed | hash ปลอดภัย + seed login ผ่าน (cost ตรงกัน) | balance ความเร็ว/ความปลอดภัย |
| E6 | **login ผิด → ข้อความ generic "อีเมลหรือรหัสผ่านไม่ถูกต้อง"** (ไม่บอกว่า field ไหนผิด) | กัน user-enumeration; ไม่โชว์ raw 500 (AUTH-2) | UX แลกความปลอดภัย — ตั้งใจ |

## F. Edge cases — การจัดการเฉพาะเคส

| # | ตัดสินใจ | ทำไม | Tradeoff |
|---|----------|------|----------|
| F1 | **EDGE-2 (ซ้ำ): server หา Entry ที่ วันที่+จำนวน+หมวด เดียวกัน → คืน `needConfirm`** ผู้ใช้ยืนยันด้วย flag `confirm=duplicate` | กดซ้ำ/บิลซ้ำจริง พบบ่อยตอนขายเร็ว ๆ; เตือนก่อนแต่ไม่ห้าม (บางทีซ้ำจริง) | ตรวจที่ server (เชื่อถือได้) ไม่ใช่แค่ disable ปุ่ม |
| F2 | **EDGE-4 (ยอดสูงผิดปกติ): เตือนเมื่อยอด ≥ ~4× ค่าเฉลี่ยหมวด** และต้องมี baseline ≥ 3 รายการ (`categoryAverageSatang`) | กันพิมพ์ 10,000 แทน 1,000; ต้องมีข้อมูลพอก่อนถึงเตือน (ไม่งั้นเตือนมั่ว) | เลือก 4× + min 3 รายการ = สมดุล false-positive ต่ำ |
| F3 | **EDGE-2 ตรวจก่อน EDGE-4** (ลำดับใน `createEntry`) | ถ้าซ้ำเป๊ะ ความเป็นซ้ำสำคัญกว่า ค่อยถามเรื่องยอดสูง | confirm flag คุมว่ายืนยันอันไหนแล้ว |
| F4 | **EDGE-3 (ข้ามประจำเฉพาะเดือน): บันทึก `RecurringSkip(month)` + ลบ Entry ที่ระบบสร้างของเดือนนั้น (transaction)** | ยอดเดือนนั้นไม่รวมรายการที่ข้าม แต่ "รูปแบบประจำยังอยู่" เดือนถัดไปกลับมาเอง | ไม่ลบ `RecurringRule`; กดยกเลิกข้ามได้ (unskip → สร้างคืน) |
| F5 | **F6 auto-generate เป็น idempotent ต่อเดือน** (เช็ค `recurringRuleId` + ช่วงเดือน ก่อนสร้าง) | เรียกตอนโหลดหน้าได้บ่อยเท่าไรก็ไม่สร้างซ้ำ (ไม่มี cron) | เลือก lazy-generate on page load แทน cron job → ไม่ต้องมี scheduler |
| F6 | **เน็ตหลุดตอนเซฟ: action คืน `{ok:false, error}` → toast + ฟอร์มไม่ปิด/ไม่ล้างค่า** | พี่นภากลัวข้อมูลหาย; ค่าที่กรอกยังอยู่ ลองใหม่ได้ | client เก็บ state จนกว่า ok |
| F7 | **ลบรายการสุดท้าย → `revalidatePath` ทุกหน้าเกี่ยวข้อง** | สรุปกลับเป็น empty state ถูกต้อง ไม่ค้างเลขเก่า | revalidate `/`,`/entries`,`/budgets`,`/profit` ทุก mutation |
| F8 | **หาร 0 ทุกจุดผ่าน `calc.ts`**: `progressPct`/`usagePct`/`marginPct` คืน 0 ถ้า target/price ≤ 0; `changePct` คืน `null` → UI โชว์ "—"; `ProgressRing` clamp `Number.isFinite` → 0 | เป้า/งบ=0 หรือเดือนก่อนไม่มีข้อมูล → ไม่มี NaN/Infinity เด็ดขาด (รวมวงแหวน) | fail-safe เป็น 0/"—" |
| F9 | **`progressPct` clamp 0–100 แต่ `usagePct` ไม่ clamp เพดาน** | งบ: ต้องเห็นว่าใช้ "เกิน" กี่ % (เช่น 101%); เป้า: progress bar/ring ไม่ควรเกิน 100% | จงใจให้ต่างกันตามความหมาย |
