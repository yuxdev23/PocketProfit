# Q&A Prep — PocketProfit (เตรียมตอบกรรมการ)

> **52 คำถามที่กรรมการน่าจะถาม + คำตอบสั้น มั่นใจ ในน้ำเสียงเจ้าของงาน.** อิงโค้ดจริงที่สร้าง.
> อ่านรอบเดียวก่อนเดโมเพื่อจำ. กลุ่ม: Business · Design/UX (brand) · Edge cases · Technical · Product/ต่อยอด.
> **แอป:** PocketProfit "รู้กำไรร้าน ทุกวัน" · `:3200` · **บัญชีเดโม** `napha@example.com` / `123456789`
> **ตัวเลขจริง:** วันนี้ +฿300 (เมื่อวาน +฿200) · เดือนนี้ +฿500 · เดือนก่อน +฿6,200 · เป้า 13,000/20,000=65% · ค่าวัตถุดิบ 8,100/8,000 · มาม่า 50% · ถุงหูหิ้ว 10%

## 1) Business Understanding (25%)

**Q1. ใครคือผู้ใช้จริง ๆ ของระบบนี้?**
"พี่นภา" นภา แซ่ลิ้ม อายุ 43 เจ้าของร้านชำ "ร้านนภาพาณิชย์" ในซอยตลาดนัดย่านบางแค เปิดร้านคนเดียวตั้งแต่ 6 โมงถึง 2 ทุ่ม ขายของจิปาถะ + ทอดกล้วย/ปาท่องโก๋หน้าร้าน. ไม่ใช่ "ร้านค้าทั่วไป" — เราเจาะจงคนเดียวเพราะทุกการตัดสินใจ UX อิงพฤติกรรมเขา.

**Q2. Pain point จริงคืออะไร?**
เขาไม่รู้กำไรสุทธิแต่ละวัน — จดสมุดบ้าง จำเอาบ้าง ข้อมูลหาย ลืม. สิ้นเดือนก็ยังไม่รู้ว่ากำไรจริงหรือขาดทุนจริง. เลยตัดสินใจผิด เช่นขายของที่จริง ๆ ขาดทุนต่อไปเรื่อย ๆ.

**Q3. ถ้าไม่มีระบบนี้ ตอนนี้เขาทำยังไง?**
จดสมุดปกอ่อนหรือแอปโน้ตในมือถือแล้วมานั่งบวกเองตอนปิดร้าน 2 ทุ่ม — เหนื่อยและพลาดง่าย. หรือไม่จดเลยใช้ "ความรู้สึก" ว่าวันนี้ขายดี ซึ่งมักคลาดจากความจริง. PocketProfit บวก-ลบให้อัตโนมัติ เห็นกำไรทันทีโดยไม่ต้องคิดเลขตอนดึก.

**Q4. ทำไมเลือกฟีเจอร์เหล่านี้ ไม่ใช่อย่างอื่น?**
ทุกฟีเจอร์แก้ pain ตรงตัว: บันทึก+แนบสลิป (ข้อมูลไม่หาย), กำไรอัตโนมัติ (ไม่ต้องคิดเลข), งบรายหมวด (รู้ว่าคุมจ่ายตรงไหน), เป้าเดือน (เขาเก็บเงินส่งลูกเรียน), margin สินค้า (รู้ว่าของไหนคุ้มขายต่อ), ค่าใช้จ่ายประจำ (ไม่ต้องจดค่าเช่าซ้ำทุกเดือน). ไม่มีฟีเจอร์ไหนใส่มาเพราะ "เท่ ๆ".

**Q5. ทำไมต้องแนบรูปสลิป/ใบเสร็จ?**
เป็นหลักฐานกันลืมว่าบิลนี้คืออะไร และไว้กระทบยอดย้อนหลังได้ (F7). พี่นภาถ่ายจากกล้องมือถือแนบได้ทันทีตอนรับของ — เร็วกว่าจำหรือจดรายละเอียด.

**Q6. ทำไม persona ถึงเจาะจงขนาดนี้ มันช่วยอะไร?**
เพราะมันบังคับทุก decision: พิมพ์ช้า → ฟอร์มคีย์เลขเป็นหลัก ปุ่มใหญ่ ≥44px. กลัวข้อมูลหาย → เซฟล้มเหลวค่าไม่หาย + เตือนก่อนซ้ำ. ไม่รู้ศัพท์บัญชี → ภาษาคน ไม่ใช่ "margin/VAT payable". ถ้าออกแบบให้ "ใครก็ได้" จะได้ของกลาง ๆ ที่ไม่เหมาะใครเลย.

**Q7. ทำไมเป็น mobile-first?**
พี่นภากรอกบนมือถือ Android จอ 6 นิ้ว ขณะมือยังจับของ/ทอนเงิน. เราออกแบบ 375px ก่อน แล้วค่อยขยายไป tablet/desktop. ฟอร์มหลักเปิดเป็น dialog เกือบเต็มจอ คีย์เลขเด้งขึ้นทันที (`inputMode`).

**Q8. วันละ 40–80 บิล กรอกทันไหม?**
ทันเพราะ flow หลักจบใน ≤3 แตะ + คีย์เลข: กด FAB → ใส่จำนวน (autofocus) → เลือกหมวด → บันทึก. default ประเภท = รายจ่าย, default วันที่ = วันนี้. ไม่ต้องกรอกอะไรที่ไม่จำเป็น.

**Q9. Secondary user มีไหม?**
มี — ลูกสาว ม.ปลาย มาช่วยขายช่วงเย็น บันทึกแทนแม่ได้. MVP เป็น single-account (ใช้บัญชีเดียวกัน) ยังไม่ทำ role. ตั้งใจตัดเพื่อคุม Time; ต่อยอดเป็น role-based ได้.

**Q10. ทำไมตัด multi-store / สต๊อก / role ออก?**
เพราะ persona คือร้านเดียวคนเดียว — ใส่ของพวกนี้คือ over-build ที่กิน Time และเสี่ยงทำของหลักไม่เนี้ยบ. เราเลือกทำ DoD + edge + validation + nice-to-have ให้ "เป๊ะ" ดีกว่าทำเยอะแบบครึ่ง ๆ. แต่ schema เผื่อต่อยอดไว้แล้ว (ดู roadmap).

**Q11. ระบบนี้ช่วยพี่นภา "ตัดสินใจ" อะไรได้บ้างเป็นรูปธรรม?**
3 อย่าง: (1) เห็นวันนี้กำไร +300 ดีกว่าเมื่อวาน → มั่นใจ; ถ้าขาดทุน → รู้ว่าต้องระวัง. (2) ค่าวัตถุดิบ 8,100 เกินงบ 8,000 → รู้ว่าต้องคุมการสั่งของ. (3) ถุงหูหิ้ว margin 10% → รู้ว่าขายแทบไม่ได้กำไร ควรขึ้นราคาหรือเลิกแถมฟรี.

**Q12. ทำไมต้องมีทั้ง "งบ" และ "เป้า" — ต่างกันยังไง?**
งบ = เพดานรายจ่าย "ต่อหมวด" (คุมว่าหมวดไหนใช้เกิน). เป้า = ภาพรวมทั้งเดือน "รายได้ที่อยากได้ + เพดานจ่ายรวม" (เขาเก็บเงินส่งลูกเรียน เลยอยากเห็นว่าใกล้เป้าหรือยัง). คนละมุม คนละการตัดสินใจ.

## 2) Design / UX & Brand (PocketProfit)

**Q13. ทำไมชื่อ "PocketProfit"? ทำไมไม่ใช้ชื่อไทย?**
เพราะมันสื่อ value ตรง pain ที่สุด — **"Profit ในกระเป๋า"** คือสิ่งเดียวที่พี่นภาอยากรู้: วันนี้เหลือกำไรเท่าไร. ชื่ออังกฤษสั้น จำง่าย ดูเป็นโปรดักต์จริง (ดีต่อกรรมการ/การทำตลาด) **คู่กับแท็กไลน์ไทย "รู้กำไรร้าน ทุกวัน"** ที่พูดกับพี่นภาตรง ๆ ในภาษาเขา. ได้ทั้ง polish และ persona ในชื่อเดียว.

**Q14. ทำไมออกแบบโทนนี้ (อุ่น ครีม-อำพัน) ไม่ทำแบบ fintech น้ำเงิน-เทา?**
เพราะ persona คือ **แม่ค้าตลาดนัด ไม่ใช่นักบัญชีองค์กร**. โทน fintech น้ำเงิน-เทาให้ความรู้สึก "เป็นทางการ/เย็น/น่ากลัว" = ผิดคน. เราเลือกโทน **"ร้านอุ่นใจ"** — ครีม + honey-amber (แดดเช้า/ทอง) + เขียวอุ่น (กำไร) + แดงอุ่น (ระวัง) ให้รู้สึกเป็นกันเอง อบอุ่น ลดความกลัวเทคโนโลยีของคนที่ "กลัวกดผิด". empathy ตรง persona คือเหตุผล ไม่ใช่แค่ความสวย.

**Q15. โลโก้สื่ออะไร?**
**ดวงอาทิตย์ + เหรียญ มีสัญลักษณ์ ฿ ตรงกลาง** — รวม 2 ความหมาย: ความอบอุ่น/เช้าวันใหม่ (อาทิตย์) + เงินทอง/กำไร (เหรียญ ฿). วาดเป็น SVG เลยคมทุกความละเอียด ใช้ได้ทั้ง favicon หัวแอป และหน้า login.

**Q16. ทำไมเอา "กำไรวันนี้" มาเป็นตัวเลขใหญ่กลางจอ + นับเลขขึ้น?**
เพราะ pain หลักคือ "ไม่รู้กำไรวันนี้" — เปิดแอปมาต้องเจอคำตอบ **ก่อนสิ่งอื่นใด** ไม่ต้องกดหา. ตัวเลขนับขึ้น (count-up) ทำให้รู้สึกมีชีวิต/น่าดู และมีประโยค "😊 ดีกว่าเมื่อวาน เก่งมาก" ให้กำลังใจคนเปิดร้านคนเดียว. นี่คือ "หัวใจอารมณ์" ของแอป.

**Q17. ทำไมมี dark mode?**
ร้านพี่นภาเปิดถึง 2 ทุ่ม กรอกตอนกลางคืน/แสงน้อย — dark mode ถนอมตา. เราทำเป็น **โหมดมืดอุ่น (near-black อมน้ำตาล)** ไม่ใช่ดำสนิทเย็น ๆ เพื่อให้ยังรู้สึกอุ่นตามแบรนด์. จำค่าไว้ (persist) เปิดครั้งหน้าเป็นโหมดเดิม และเคารพ `prefers-reduced-motion`.

**Q18. ทำไมใช้วงแหวน (ring) แสดงเป้า ไม่ใช่แค่ตัวเลข/แถบ?**
"65% ของเป้า" เป็นภาพวงกลมเต็ม-ไม่เต็ม **อ่านเร็วกว่าตัวเลขล้วน** และสื่ออารมณ์ "ใกล้ถึงเป้าเก็บเงินส่งลูกเรียนแค่ไหน" ได้ดี. วงนับขึ้นให้รู้สึก progress จริง; เพดานรายจ่ายใช้วงแดงเตือนทันทีเมื่อเกิน.

**Q19. micro-copy ทำไมใช้ภาษาให้กำลังใจ ไม่ใช่ศัพท์บัญชี?**
เพราะ persona ไม่รู้ศัพท์บัญชี + เปิดร้านคนเดียวเหนื่อย. ภาษาต้องเป็น "เพื่อน" ไม่ตัดสิน — ขาดทุนขึ้น "🌱 วันนี้ขาดทุน ไม่เป็นไร พรุ่งนี้สู้ใหม่" (ยังเห็นชัดด้วยสีแดง+▼ แต่ไม่ทำให้รู้สึกแย่). สร้างความผูกพัน + ลดความกลัวเทคโนโลยี.

**Q20. ดีไซน์สวยแบบนี้ ไปแตะ logic การเงินไหม — ตัวเลขยังเชื่อถือได้ไหม?**
ไม่แตะเลย. warm UI ทั้งหมดเป็น **presentation layer** (design tokens ใน `globals.css` + components) — เปลี่ยนหน้าตาโดยไม่แตะ money/calc/queries/validation. เราทำดีไซน์ **หลัง** acceptance ครบ 24/24 และตัวเลข DoD ยังเป๊ะเหมือนเดิมหลังรีดีไซน์. เป็นหลักฐานว่า logic แยกชั้นดีจริง.

**Q21. accessibility ดูแลยังไง?**
(1) กำไรไม่พึ่งสีอย่างเดียว — มีเครื่องหมาย −/▼ + ข้อความกำกับ (color-blind safe). (2) ทุก animation (count-up/วงแหวน/fade) เคารพ `prefers-reduced-motion`. (3) dark/light คุม contrast ระดับ AA ทั้งคู่. (4) ปุ่ม ≥44px, focus ring ชัด, aria-label ครบ. (5) theme toggle กัน hydration mismatch ด้วย mount-guard.

## 3) Edge Cases ("ถ้า… จะเกิดอะไร")

**Q22. ถ้ายังไม่มีข้อมูลเลย (เปิดครั้งแรก) หน้าจอเป็นยังไง?**
ทุกหน้ามี empty state ชัดเจน ไม่โชว์ NaN/กราฟพัง: hero ขึ้น ฿0 + "วันนี้ยังไม่มีรายการ แตะ + บันทึกบิลแรก", กราฟขึ้น "ยังไม่มีข้อมูลพอแสดงกราฟ". ทดสอบจริงด้วย user ใหม่แล้ว — เห็น ฿0 ทุกที่ ไม่มี NaN.

**Q23. ถ้าตั้งเป้า/งบ = 0 แล้วคิด % จะหารด้วยศูนย์ไหม?**
ไม่ — ทุกการหารผ่าน `calc.ts` ที่ guard ไว้. `progressPct`/`usagePct`/`marginPct` ถ้า target/price ≤ 0 คืน 0 ทันที ไม่ใช่ NaN/Infinity. แม้แต่วงแหวน progress ก็ clamp `Number.isFinite` → 0.

**Q24. ถ้ากดบันทึกซ้ำ 2 ครั้ง (double-submit) จะได้รายการซ้ำไหม?**
กัน 2 ชั้น: (1) ปุ่มบันทึก disable ระหว่างกำลังบันทึก. (2) ที่ server ตรวจว่ามีรายการ วันที่+จำนวน+หมวด เดียวกันไหม ถ้ามีจะเด้ง "อาจเป็นรายการซ้ำ" ให้ยืนยันก่อน (EDGE-2). ตรวจที่ server เลยกัน bypass ได้จริง.

**Q25. ถ้าพิมพ์เลขผิด เช่น 10,000 แทน 1,000 ระบบรู้ไหม?**
รู้ — EDGE-4: ถ้ายอด ≥ ~4 เท่าของค่าเฉลี่ยหมวดนั้น (และหมวดมีประวัติ ≥ 3 รายการ) จะเตือน "ยอดสูงกว่าปกติ" พร้อมบอกค่าเฉลี่ย. ถ้ายอดสูงจริง (ซื้อของล็อตใหญ่) ก็กดยืนยันผ่านได้.

**Q26. ทำไม EDGE-4 ต้องมี baseline 3 รายการก่อนถึงเตือน?**
ถ้าเตือนตั้งแต่รายการแรก ๆ จะเตือนมั่ว (ยังไม่มีค่าเฉลี่ยที่น่าเชื่อ). รอให้มีอย่างน้อย 3 รายการในหมวดก่อนแล้วค่อยเทียบ — false-positive ต่ำ ไม่กวนพี่นภา.

**Q27. ถ้าแก้รายการย้อนหลังล่ะ — ของเดิมหายไหม?**
ไม่หาย. EDGE-1/F7: บังคับกรอกเหตุผล (≥3 ตัวอักษร) ก่อนบันทึก แล้วเก็บประวัติทุก field ที่เปลี่ยน — ค่าก่อน → ค่าหลัง + เหตุผล + เวลา. การ update + บันทึก revision อยู่ใน transaction เดียว.

**Q28. ถ้าแก้ยอดแล้ว รูปใบเสร็จที่แนบไว้ยังอยู่ไหม?**
อยู่ — รูปติดกับรายการ ไม่ถูกลบตอนแก้. ในประวัติเห็นว่ายอดเปลี่ยนจากเท่าไรเป็นเท่าไร และรูปเดิมยังเปิดดูได้ (ตรงตาม F7).

**Q29. ถ้าค่าใช้จ่ายประจำเดือนนี้ไม่เกิด เช่น เดือนนี้ไม่จ่ายค่าเช่า?**
กด "ข้ามเดือนนี้" ได้ (EDGE-3): บันทึก skip ของเดือนนั้น + ลบรายการที่สร้างอัตโนมัติของเดือนนั้น → ยอดเดือนนี้ไม่รวมค่าเช่า. แต่ "รูปแบบรายการประจำยังอยู่" เดือนถัดไปกลับมาสร้างเองปกติ. กดยกเลิกการข้ามได้ รายการจะถูกสร้างคืน.

**Q30. ถ้ากำไรติดลบ (ขาดทุน) หน้าจอบอกชัดไหม?**
ชัดมาก — ตัวเลขสีแดง + เครื่องหมาย "−" + ▼ + ข้อความ "วันนี้ขาดทุน ไม่เป็นไร พรุ่งนี้สู้ใหม่". ไม่พึ่งสีอย่างเดียว (color-blind safe).

**Q31. ถ้าวันนี้กรอกตอน 5 ทุ่ม มันนับเป็นวันไหน?**
วันนี้ (เวลาไทย) — เราตัดยอดตาม Asia/Bangkok UTC+7 ไม่ใช่ UTC. ถ้าใช้ UTC ตอน 5 ทุ่มไทยจะข้ามไปวันถัดไปแล้วยอด "วันนี้" ผิด. เราคำนวณ offset เองทุกจุดใน `dates.ts`.

**Q32. ถ้าเลือกวันที่ในอนาคตล่ะ?**
บล็อก — ขึ้น "เลือกวันที่ในอนาคตไม่ได้". `<input type="date">` ก็ตั้ง max=วันนี้ ป้องกันชั้นแรกแล้ว.

**Q33. ถ้าเน็ตหลุดตอนกดเซฟ ข้อมูลที่กรอกหายไหม?**
ไม่หาย — ถ้าบันทึกล้มเหลว เราขึ้น toast "บันทึกไม่สำเร็จ ลองอีกครั้ง — ข้อมูลที่กรอกยังอยู่" และฟอร์มไม่ปิด ไม่ล้างค่า. ตรงกับความกลัวข้อมูลหายของเขา.

**Q34. ถ้าลบรายการสุดท้ายของวัน/เดือน สรุปจะค้างเลขเก่าไหม?**
ไม่ — ทุก mutation `revalidatePath` หน้าที่เกี่ยวข้องทั้งหมด. ลบรายการสุดท้ายแล้วสรุปกลับเป็น empty state ถูกต้อง ไม่ค้างตัวเลขเดิม.

**Q35. ถ้ากรอกตัวอักษร/ค่าว่าง/ติดลบ/ทศนิยม 3 ตำแหน่ง ในช่องเงิน?**
บล็อกทุกกรณีพร้อมข้อความไทยเจาะจง: ว่าง→"กรุณากรอกจำนวนเงิน", ตัวอักษร→"กรอกเป็นตัวเลขเท่านั้น", ≤0→"จำนวนเงินต้องมากกว่า 0 บาท", ทศนิยม>2→"ใส่ทศนิยมได้ไม่เกิน 2 ตำแหน่ง". ไม่มี raw error หลุด.

**Q36. ถ้าใส่เลขมหาศาล?**
มีเพดาน 10,000,000 บาท → เกินนั้นขึ้น "จำนวนเงินสูงเกินไป กรุณาตรวจสอบอีกครั้ง". เพดานนี้เกินยอดจริงของร้านชำมาก แต่กันพิมพ์พลาดยาว ๆ.

**Q37. ถ้าเดือนก่อนไม่มีข้อมูล จะเทียบ % ยังไง — โชว์ Infinity ไหม?**
ไม่ — `changePct` คืน `null` ถ้าเดือนก่อน = 0 แล้ว UI โชว์ "—" + "(ไม่มีข้อมูลเดือนก่อน)". ไม่มีทางเห็น Infinity% หรือ NaN.

**Q38. ถ้าราคาขายต่ำกว่าต้นทุน (margin ติดลบ)?**
`marginPct` คืนค่าติดลบได้จริง (ไม่ clamp) เพื่อให้เห็นว่าขาดทุนต่อหน่วย + ขึ้นเตือน "ราคาขายต่ำกว่าต้นทุน". และถ้า margin ต่ำกว่าเกณฑ์ (default 20%) จะมี alert บนหน้าหลักด้วย (เช่น ถุงหูหิ้ว 10%).

**Q39. ถ้าผู้ใช้ A กับ B มีรายการเหมือนกันเป๊ะ จะเห็นข้ามกันไหม?**
ไม่มีทาง — ทุก query ผูก `userId` เสมอ. แม้รู้ id ของอีกคนก็เปิด/แก้/ลบไม่ได้ (เช็ค ownership ทุก action — กัน IDOR).

## 4) Technical

**Q40. ใช้ stack อะไร ทำไม?**
Next.js 15 (App Router) + Server Actions, Prisma + SQLite, zod, react-hook-form, recharts, Tailwind + shadcn/ui, next-themes (dark mode). เลือกเพราะ logic การเงินอยู่ฝั่ง server ทั้งหมดผ่าน server action — โค้ดน้อย ปลอดภัย ไม่ต้องแยก API. SQLite ทำให้เดโม/seed ได้ในไฟล์เดียว และย้ายเป็น Postgres ภายหลังแค่เปลี่ยน datasource.

**Q41. เก็บเงินยังไงไม่ให้ตัวเลขเพี้ยน?**
เก็บเป็น integer "สตางค์" ทุกที่ (1 บาท = 100 สตางค์) ไม่เก็บ float บาทเลย. float มี drift (0.1+0.2≠0.3) → กำไรเพี้ยนสะสม. การแปลงบาท↔สตางค์อยู่จุดเดียวใน `money.ts` (`Math.round(n*100)`). บวก/ลบ/รวมเป็น integer ทั้งหมด.

**Q42. การตัดยอด "วันนี้/เดือนนี้" ตามเวลาไทยทำยังไง?**
เก็บ `occurredAt` เป็น instant ที่ "เที่ยงวันไทย" (05:00Z) ของวันนั้น — อยู่กลางวันไทยเสมอ ไม่มีทางปัด/DST ข้ามวัน. เวลา group คำนวณช่วง `[gte, lt)` ของวัน/เดือนตาม UTC+7 แล้ว filter ที่ DB (`bkkDayRange`/`bkkMonthRange`). group/sum ที่ DB เร็วและถูก.

**Q43. แยก occurredAt กับ createdAt ทำไม?**
`occurredAt` = วันที่บิลเกิดจริง (ผู้ใช้เลือก back-date ได้), `createdAt` = เวลาที่กดบันทึก. สรุปวัน/เดือน group ด้วย `occurredAt` เพื่อให้บันทึกย้อนหลังลง "เดือนที่ถูกต้อง" ไม่ใช่เดือนที่กรอก.

**Q44. Auth/session ทำงานยังไง?**
email+password, hash ด้วย bcrypt (cost 10). login สำเร็จ → สร้าง session token สุ่ม 32 bytes เก็บใน DB + cookie httpOnly, sameSite=lax, อายุ 30 วัน. ทุกหน้าใน (app) เรียก `requireUser()` — ไม่มี session เด้งไป /login. logout ลบ row + ล้าง cookie. ใช้ session ใน DB (ไม่ใช่ JWT) เพราะเพิกถอนได้.

**Q45. Per-user isolation มั่นใจได้ยังไงว่าไม่รั่ว?**
ทุก query ใน `queries.ts` ผูก `userId` เป็นเงื่อนไขเสมอ. action ที่รับ id จาก client (แก้/ลบ/ดูประวัติ) ใช้ `findFirst({id, userId})` เช็ค ownership ก่อนทำเสมอ กัน IDOR. tech-lead review แล้วยืนยันว่า bound ครบทุกจุด.

**Q46. Validation ทำสองที่ (client+server) ทำไม?**
ใช้ zod schema "ชุดเดียวกัน" ทั้งสองฝั่ง: client (react-hook-form) ตอบไว, server re-validate ทุก action ก่อนเขียน DB กันคน bypass client/ยิง request ตรง. ข้อความ error ตรงกันเป๊ะเพราะ schema เดียวกัน.

**Q47. ไม่โชว์ raw 500 ยังไง?**
ทุก server action ครอบ try/catch แล้วคืน `{ok:false, error:"เกิดข้อผิดพลาด กรุณาลองใหม่อีกครั้ง"}` เป็นข้อความไทย → toast. login ผิดคืนข้อความ generic. ไม่มี stack trace/500 ดิบหลุดถึงผู้ใช้.

**Q48. ค่าใช้จ่ายประจำสร้างอัตโนมัติยังไง — มี cron ไหม?**
ไม่มี cron. ใช้ lazy-generate ที่ idempotent: ตอนโหลดหน้าเรียก `ensureRecurringForCurrentMonth` — สำหรับทุก rule ที่ active + ยังไม่ถูกข้าม + ยังไม่เคยสร้างเดือนนี้ → สร้าง 1 รายการ. เช็ค `recurringRuleId` + ช่วงเดือนเป็นกุญแจกันซ้ำ เลยรีเฟรชกี่ครั้งก็ไม่สร้างซ้ำ. ข้อดี: ไม่ต้องมี scheduler ให้พัง.

**Q49. ความปลอดภัยอื่น ๆ มีอะไรบ้าง?**
(1) Prisma parameterized 100% ไม่มี raw SQL → กัน SQL injection. (2) password bcrypt ไม่เคยส่ง hash ออก client. (3) login generic message กัน user-enumeration. (4) upload sanitize ชื่อไฟล์ + จำกัดเฉพาะรูป ≤5MB + กัน path traversal. (5) CSV export กัน formula-injection (นำหน้า `'` ถ้าค่าขึ้นต้น `= + - @`). (6) cookie httpOnly กัน XSS ขโมย session.

**Q50. ถ้าผู้ใช้เยอะขึ้น / ต้องการ backend จริง จะ scale ยังไง?**
โค้ด query แยกชั้นอยู่แล้ว — ย้าย SQLite → Postgres แค่เปลี่ยน datasource ไม่ต้องแก้ logic. มี index ที่ `(userId)` และ `(userId, occurredAt)` รองรับ query หลัก. session อยู่ DB scale แนวนอนได้. การคำนวณ sum/group ทำที่ DB ไม่ใช่ JS เลยไม่พังเมื่อข้อมูลโต.

**Q51. จะเทสต์ระบบนี้ยังไง?**
ตอนนี้ verify ด้วย: (1) seed ที่ reproduce ทุกตัวเลข DoD เป๊ะ (วันนี้ +300, เดือนก่อน +6,200, เป้า 65%, เกินงบ 8,100/8,000, margin 50%/10%). (2) QA เดินจริงใน running app (headless Chrome + เช็ค DB). (3) tech-lead audit security. ต่อยอด: unit test `calc.ts`/`dates.ts`/`money.ts` (pure functions) + e2e Playwright สำหรับ flow หลัก.

**Q52. VAT คิดยังไง / CSV ภาษาไทยเพี้ยนไหม?**
VAT **inclusive** — ยอดที่กรอกคือยอดรวม VAT แล้ว (ตรงใบเสร็จ) เราแยกส่วน VAT ด้วย `total − total/(1+rate/100)`; หน้า /budgets สรุปภาษีขาย/ซื้อ/สุทธิรายเดือน. CSV ใส่ **UTF-8 BOM** นำหน้า → Excel อ่านไทยถูก, escape comma/newline, ผูก userId, กัน formula-injection.

## 5) Product / ต่อยอด (Vision)

**Q53. อะไรคือสิ่งต่อไปที่จะทำ ถ้ามีเวลาเพิ่ม?**
3 อันดับแรก: (1) **สรุปอัตโนมัติ/insight** — "สัปดาห์นี้ค่าวัตถุดิบขึ้น 20%" แจ้งเชิงรุก. (2) **LINE integration** — บันทึกผ่านแชต LINE (พี่นภาใช้ LINE ทุกวัน) + ส่งกำไรวันนี้เข้า LINE ทุกเย็น. (3) **PWA + offline queue** — เน็ตหลุดก็กรอกได้ sync ทีหลัง. จัดลำดับตาม "ลดแรงกรอก" + "ทำให้ตัวเลขมีประโยชน์เชิงตัดสินใจมากขึ้น" — รายละเอียดเต็มใน `roadmap.md`.

**Q54. ฟีเจอร์ที่ "ตั้งใจไม่ทำ" ตอนนี้ มีอะไรบ้าง แล้วทำไม?**
Multi-store, สต๊อกเต็มรูป, role-based, ใบกำกับภาษีเต็ม, offline-sync เต็ม. ตัดเพื่อคุม Time และโฟกัสทำของหลักให้เป๊ะ — แต่ schema เผื่อไว้ (แยก income/expense kind, snapshot ชื่อ, recurring + skip) ต่อยอดได้โดยไม่ต้องรื้อ. วินัยเรื่อง scope คือสิ่งที่ทำให้ DoD ครบและไม่มีบั๊ก.

**Q55. ระบบนี้ขายเป็นธุรกิจได้ไหม?**
ได้ — ร้านชำ/แผงตลาด/ร้านอาหารเล็กในไทยมีเป็นล้านร้าน ส่วนใหญ่ยังจดสมุด. โมเดล freemium: ฟรีสำหรับร้านเดียว, จ่ายรายเดือนเมื่อต้องการหลายสาขา/พนักงาน/รายงานภาษี. จุดต่างคือ PocketProfit "ออกแบบมาเพื่อคนกรอกมือถือคนเดียวที่ไม่รู้บัญชี" ไม่ใช่โปรแกรมบัญชีที่ซับซ้อน — กรอกเร็ว ภาษาคน อุ่นใจ.
