# Roadmap — PocketProfit (ต่อยอดเกินโจทย์)

> Vision หลังส่งมอบ — ต่อยอดจากของที่สร้างจริง โดย **ไม่ over-build ตอนนี้**. ทุกข้อมี user value ชัด + อิงสถาปัตยกรรมที่วางไว้แล้ว (สตางค์ integer, per-user, recurring+skip, snapshot ชื่อหมวด, Prisma สลับ DB ได้, warm UI แยกชั้น token/component).
> **แอป:** PocketProfit — "รู้กำไรร้าน ทุกวัน". ของหลักเป๊ะ (24/24) + แบรนด์อุ่นพร้อมแล้ว → ต่อยอดให้ "ลดแรงกรอก" และ "ตัวเลขมีประโยชน์เชิงตัดสินใจมากขึ้น".

---

## A. ฟีเจอร์ถัดไป (เรียงตามคุณค่าต่อพี่นภา + ต้นทุนทำ)

| # | ฟีเจอร์ | คุณค่าต่อผู้ใช้ (พี่นภา) | ต่อยอดจากอะไร | ความยาก |
|---|---------|--------------------------|----------------|---------|
| 1 | **บันทึกผ่าน LINE / LINE summary รายวัน** | พี่นภาใช้ LINE ทุกวันอยู่แล้ว — พิมพ์ "ขายหน้าร้าน 120" ใน LINE OA แล้วระบบบันทึกให้ + ส่ง "กำไรวันนี้ +฿xxx" (พร้อม emoji กำลังใจแบบใน hero) เข้า LINE ทุกเย็น 2 ทุ่ม | ต่อ webhook → server action `createEntry` เดิม; parsing ข้อความ | กลาง |
| 2 | **Insight/แจ้งเตือนเชิงรุก** | ไม่ต้องเปิดแอปหา — ระบบบอกเอง "ค่าวัตถุดิบสัปดาห์นี้ขึ้น 20% จากปกติ" / "วันนี้ขาดทุนติดต่อ 3 วัน" | มี `categoryAverageSatang` + sum รายวัน/เดือนอยู่แล้ว ต่อยอดเป็น trend detection | กลาง |
| 3 | **PWA + offline queue + ติดตั้งเป็นแอป** | เน็ตในร้านหลุดเป็นช่วง ๆ — กรอกได้ตลอด เก็บคิวไว้ sync เมื่อเน็ตกลับ; ปักไอคอน PocketProfit (sun-coin) บนหน้าจอ Android | ตอนนี้ "เซฟล้มเหลวค่าไม่หาย" แล้ว + มี brand-mark SVG เป็น icon → ต่อเป็น service worker + IndexedDB queue + manifest | กลาง-สูง |
| 4 | **รายงาน/สรุปรายเดือนแบบ PDF + ภ.พ.30 ช่วย** | สิ้นเดือนกดปุ่มเดียวได้สรุปกำไร + ยอด VAT ไปยื่นภาษี/ส่งบัญชี (มี brand header) | มี N1 (CSV) + N3 (VAT summary) อยู่แล้ว → ต่อเป็น PDF/แบบฟอร์ม | กลาง |
| 5 | **Dashboard กราฟแนวโน้ม + เปรียบเทียบหลายเดือน** | เห็นภาพรวมว่าธุรกิจดีขึ้น/แย่ลง ตัดสินใจระยะยาว | มี `monthlyNetSeries` (6 เดือน) + recharts + warm chart tokens แล้ว → เพิ่มมุมมอง | ต่ำ |
| 6 | **สแกนสลิป → กรอกอัตโนมัติ (OCR)** | ถ่ายใบเสร็จแล้วระบบเดายอด/วันที่ให้ ลดการพิมพ์ของพี่นภา (พิมพ์ช้า) | มี upload รูปแล้ว → ต่อ OCR เติม `amount`/`date` ในฟอร์ม | สูง |
| 7 | **เป้า/งบแบบหลายเดือน + auto-rollover** | ตั้งงบครั้งเดียวใช้ต่อทุกเดือน ไม่ต้องตั้งใหม่ | `Goal.month`/`budget` เป็นรายเดือนอยู่แล้ว → เพิ่ม template/copy เดือนก่อน | ต่ำ |
| 8 | **หมวด/สินค้า "ที่ใช้บ่อย" ปักหมุด + quick-add** | ร้านขายของซ้ำ ๆ — แตะปุ่มลัด "มาม่า 6 บาท" บันทึกได้ใน 1 แตะ | มี Product (ต้นทุน/ราคา) + Category อยู่แล้ว → ผูก quick-add | ต่ำ-กลาง |

**จัดลำดับยังไง:** ให้น้ำหนัก 2 แกน — **(ก) ลดแรงกรอก** ของพี่นภา (LINE, OCR, quick-add) และ **(ข) ทำให้ตัวเลขมีประโยชน์เชิงตัดสินใจมากขึ้น** (insight, รายงาน, แนวโน้ม). อันดับ 1–2 ตอบทั้งสองแกนและต้นทุนไม่สูง → ทำก่อน.

## B. Technical evolution (โตเป็น production)

| ด้าน | ตอนนี้ | ก้าวต่อไป | ทำไม/หมายเหตุ |
|------|--------|-----------|----------------|
| **Database** | SQLite (ไฟล์เดียว) | Hosted Postgres (Neon/Supabase) | แค่เปลี่ยน `datasource` — query/logic ไม่แตะ. รองรับหลายผู้ใช้/concurrent writes |
| **Storage รูป** | `public/uploads/<userId>/` (local) | S3/R2 + signed URL | ตอนนี้ sanitize + จำกัด type/size แล้ว → ย้ายไป object storage เมื่อ deploy หลายเครื่อง |
| **Auth** | session token ใน DB + cookie | + OAuth (LINE Login/Google), 2FA option | session อยู่ DB อยู่แล้ว เพิ่ม provider ได้; LINE Login เหมาะ persona ไทย |
| **Recurring gen** | lazy idempotent ตอนโหลดหน้า | cron/queue job (เมื่อมีผู้ใช้เยอะ) | ตอนนี้ไม่พึ่ง scheduler (ดี); เมื่อ scale ค่อยย้ายไป background job |
| **Mobile** | mobile-first web (responsive) + dark mode | PWA → ติดตั้งบนจอ Android / native ภายหลัง | PWA คุ้มสุดสำหรับ persona; native เมื่อต้องการกล้อง/notification ลึก |
| **Design system** | warm tokens (`globals.css`) + components (brand-mark, profit-hero, progress-ring) | แยกเป็น token package + เพิ่มธีมตามฤดู/เทศกาล (เช่น โทนตรุษจีน) | UI แยกชั้นจาก logic แล้ว → เพิ่ม/เปลี่ยนธีมได้โดยไม่แตะการเงิน |
| **Testing** | seed reproduce DoD + QA เดินจริง + tech-lead audit | unit test (`calc`/`dates`/`money` เป็น pure func) + e2e Playwright | pure functions เทสต์ง่ายมาก ควรเป็นด่านแรกของ CI |
| **Observability** | toast error ฝั่ง user | error tracking (Sentry) + audit log ระดับ action | กัน raw 500 แล้ว → เก็บ error จริงไว้ดูฝั่ง dev |
| **i18n/timezone** | Asia/Bangkok hardcoded (ตรง persona) | แยก timezone ต่อผู้ใช้ถ้าขยายต่างจังหวัด/ต่างประเทศ | `dates.ts` รวม logic จุดเดียว แก้ที่เดียว |

## C. Business angle (ถ้าจะทำเป็นผลิตภัณฑ์จริง)

- **ตลาด:** ร้านชำ/แผงตลาด/ร้านอาหารตามสั่ง/คาเฟ่เล็กในไทยมีหลักล้านร้าน ส่วนใหญ่ยัง "จดสมุด/จำเอา". กลุ่มนี้ถูกมองข้ามโดยโปรแกรมบัญชีที่ซับซ้อนเกินไป.
- **จุดต่าง (moat):** PocketProfit ออกแบบมาเพื่อ **"คนกรอกมือถือคนเดียวระหว่างขายของ ที่ไม่รู้ศัพท์บัญชี"** — ไม่ใช่โปรแกรมบัญชี. กรอกเร็ว ภาษาคน กันผิด/กันหาย + **แบรนด์อุ่นเป็นกันเอง** ("รู้กำไรวันนี้" หน้าสุด) ที่ทำให้คนกลัวเทคโนโลยีกล้าใช้. คู่แข่ง (Excel, แอปบัญชีใหญ่) แพ้เรื่อง UX + ความอบอุ่นสำหรับกลุ่มนี้.
- **โมเดลรายได้:** Freemium — ฟรีสำหรับร้านเดียว/ฟีเจอร์หลัก; เก็บรายเดือนเมื่อต้องการ **หลายสาขา + พนักงาน (role) + รายงานภาษี/ส่งบัญชี + LINE/insight**. ราคาระดับ "ถูกกว่าจ้างนักบัญชี 1 ชม./เดือน".
- **Go-to-market:** เข้าผ่าน LINE OA + กลุ่มแม่ค้าออนไลน์ + ร่วมกับตลาดนัด/แฟรนไชส์ร้านชำ. ฟีเจอร์ LINE (A1) เป็นทั้ง product และช่องทางโต. แบรนด์ PocketProfit + โลโก้ sun-coin จำง่าย บอกต่อปากต่อปากในกลุ่มแม่ค้าได้.

## D. สิ่งที่ "จงใจไม่ทำตอนนี้" (วินัย scope) → ทำเมื่อมีสัญญาณจริง

| ตัด | จะทำเมื่อ | ของที่เผื่อไว้แล้วใน schema |
|-----|-----------|-----------------------------|
| Multi-store | ผู้ใช้ขอจัดการ >1 ร้าน | scope ทุกอย่างใต้ userId อยู่แล้ว → เพิ่มชั้น `Store` ได้ |
| Role-based (admin/staff) | ลูกจ้างต้องแยกสิทธิ์จากเจ้าของ | User/Session แยกแล้ว → เพิ่ม role + store membership |
| สต๊อก/คงคลังเต็ม | ต้องการ track จำนวนคงเหลือ | มี Product (ต้นทุน/ราคา) แล้ว → เพิ่ม stock + ตัดตอนขาย |
| ใบกำกับภาษีเต็ม/double-entry | ลูกค้าจด VAT ต้องการเอกสารทางการ | มี VAT ต่อรายการ + สรุปรายเดือนแล้ว → ต่อยอดออกเอกสาร |

> **หลักคิด:** เราชนะด้วยการทำของหลักให้ "เป๊ะและน่าเชื่อถือ" แล้วห่อด้วยแบรนด์ที่ "อุ่นและเข้าใจคนใช้" — จากนั้นต่อยอดตามสัญญาณผู้ใช้จริง ไม่ใช่ใส่ทุกอย่างตั้งแต่แรกแล้วไม่มีอะไรดีจริง. Vision ชัด แต่ไม่ over-build วันนี้.
